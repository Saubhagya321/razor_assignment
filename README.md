# WooCommerce MCP Connector

A read-only [MCP](https://modelcontextprotocol.io) server that lets an agent (Claude Desktop, Razorpay Agent Studio, or any MCP host) read orders and customers from a WooCommerce store. Running example used throughout: **"find open orders for customer X."**

Full design rationale lives in [SPEC.md](SPEC.md). This README is the practical "how do I run it" doc.

## Architecture

```
Agent host -> MCP client -> [ MCP server (this repo) ] -> WooCommerce REST API
                                |- tools (list/search/get/find)
                                |- sanitizer (allowlist + masking)
                                |- HTTP client (auth, retry, 429 handling)
                                `- config (base URL, key, secret from env)
```

**One codebase, two backends.** The mock-vs-real choice lives only in `WC_BASE_URL`. There is no `if mock:` branch anywhere in `src/wc_connector/` — the tools, sanitizer, and HTTP client run identically against both.

- **Real WooCommerce store** (primary, see [INSTALL.md](INSTALL.md)): what the connector is built and demonstrated against.
- **Mock server** (`mock/app.py`, FastAPI, built from real saved fixtures in `mock/fixtures/`): a zero-setup option for reviewers, and the only way to deterministically trigger 401/429/5xx failure modes a healthy real store won't produce on demand.

## Quick start with the mock (3 commands)

```bash
pip install -r requirements.txt
cp .env.example .env          # defaults already point at the mock (WC_BASE_URL=http://localhost:8080)
python -m mock.app &          # starts the mock WooCommerce server on :8080
```

Then run the test suite against it:

```bash
pytest
```

62 tests should pass — covering retries/backoff, the sanitizer (PII/injection/secret safety), config validation, throttling, and the MCP protocol layer itself (tool annotations, `isError`, output-schema validation, stdout-only protocol framing). See `SPEC.md` section 9 for the full list and which test covers which item.

To talk to the mock as an agent would, connect an MCP host (below) with `.env`'s default `WC_BASE_URL`.

## Real store (primary path)

The real-store setup (Docker WordPress + MySQL + WooCommerce behind an HTTPS proxy, a read-only REST API key, and `scripts/seed_store.py` for fake demo data) is documented step by step in **[INSTALL.md](INSTALL.md)**.

Once the store is up and seeded:

1. Create a **Read-only** REST API key (WooCommerce → Settings → Advanced → REST API).
2. Put it in `.env` (copied from `.env.example`):
   ```
   WC_BASE_URL=https://localhost:8443
   WC_CONSUMER_KEY=ck_...
   WC_CONSUMER_SECRET=cs_...
   WC_CA_BUNDLE=./certs/...        # if the local proxy uses a self-signed cert
   ```
3. Run `python scripts/smoke_real.py` — a manual smoke/demo script (not part of the pytest suite, since it hits a live store) that exercises every tool, the 404 and "no customer match" paths, input validation, and a deliberately-wrong-credentials call proving `AUTH_FAILED` with zero retries. Nothing it prints ever includes the real consumer key or secret.

The demo shown for submission is run against this real store, not the mock — the mock exists for deterministic failure-mode testing and reviewer convenience, not as the "real" demonstration.

## Connecting an MCP host (stdio)

The server speaks stdio: stdout carries only JSON-RPC protocol messages, all logs go to stderr (see `tests/test_stdio_protocol.py` for a test that proves this end-to-end over a real subprocess).

Example config for Claude Desktop (`%APPDATA%\Claude\claude_desktop_config.json` on Windows, `~/Library/Application Support/Claude/claude_desktop_config.json` on macOS):

```json
{
  "mcpServers": {
    "wc-connector": {
      "command": "/path/to/python",
      "args": ["-m", "wc_connector.server"],
      "cwd": "/path/to/this/repo",
      "env": {
        "PYTHONPATH": "/path/to/this/repo/src"
      }
    }
  }
}
```

`cwd` should be the repo root so `server.py`'s `load_dotenv()` picks up the `.env` file there. Fully quit and relaunch the host after editing its config (most hosts cache MCP connections on startup).

The exact tool specification (names, descriptions, JSON-schema inputs/outputs, annotations) that any host should see is checked into [`docs/tool-spec.json`](docs/tool-spec.json), regenerated by `python scripts/dump_tool_spec.py`. A test (`tests/test_tool_spec_matches_server.py`) fails if the checked-in file ever drifts from the live server.

**Note on Agent Studio:** no public spec for third-party connectors was found at build time. This targets standard MCP over stdio; an adapter may be needed for other hosts.

## Assumptions and limitations

- **stdio only.** This is a local-development transport choice. A production deployment should be a remote HTTP server with MCP OAuth 2.1 so the platform can verify callers — see `docs/capabilities.md` and SPEC.md section 12 for the long-term fix.
- **One shared API key**, not per-user credentials: no per-caller permissions or audit trail. Long-term fix: per-merchant credentials in a secret manager, with rotation.
- **Read-only by design**: the key itself has Read permission only; there is no create/update/delete path in the code at all.
- **Masking reduces exposure, not a guarantee**: the sanitizer allowlists and masks what the connector returns, but doesn't control what the MCP host or platform itself logs or stores downstream.
- **No date/amount/product filters**: only status and customer (id or email) are exposed as search filters.
- **A default WooCommerce store may never return a real 429** (no built-in rate limiting) — the 429 retry/backoff/budget behavior is proven against the mock (`tests/test_client.py`, `tests/test_client_429_always_scenario.py`), not the real store, because there is no reliable way to make a healthy real store rate-limit itself on demand.
- **Guest orders** (`customer_id: 0`) cannot be reliably matched to a customer by email **[VERIFY against your store's actual guest-checkout behavior]**.
- **The mock can drift from the real API** over time; it was built from real saved fixtures (`mock/fixtures/`), not from memory, to reduce that risk, but it is still a hand-maintained approximation.

See [`docs/capabilities.md`](docs/capabilities.md) for the full can/cannot list.

## MCP features deliberately not used

- **Resources / prompts**: tools only — tools are model-controlled, which fits "agent decides to look up orders."
- **Sampling**: not needed; this is a plain data reader.
- **Roots**: not needed; no file-system access.
- **Notifications/progress**: not implemented in v1; would go over the logging channel if added, never stdout.
- **Streamable HTTP**: out of scope for v1 (see limitations above).
